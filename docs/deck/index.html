n1k1

SQL++ for local files and more —
with a high performance query engine that's

1 · what & why

Query local files and more

no server · no import step · no schema to declare

what & why

One binary, pointed at local or remote
paths & directories

$ n1k1 -c "SELECT id, customer, total FROM orders
           WHERE total > 200 ORDER BY total DESC" examples/shop
  • Inspirations: sqlite3 / duckdb,
    but the query language (SQL++) is built for nested JSON
    and the scan layer handles directory trees of mixed data file formats.
  • File formats are discovered per file — no CREATE TABLE:

JSON / JSONLCSV / TSVYAML TOMLParquetIceberg .gzPDF / Offices3:// gs:// abfs://

Also compiles to wasm: the playground runs n1k1's engine client-side in a browser.

what & why

Not a database server (yet)

  • Read-oriented: no UPDATE/DELETE, no transactions.
    Writing is materialization only (CREATE TEMP KEYSPACE, INSERT INTO a .jsonl/Parquet file).
  • Pure Go, CGO_ENABLED=0, cross-compiles to Linux/macOS/Windows on amd64 + arm64 —
    and to GOOS=js/wasm.
  • Goroutine-per-connection sessions — n1k1 is a CLI and a library, not a daemon yet.
  • Binary anatomy: full build ~102 MB;
    -tags trim (drop lakehouse + cloud SDKs) ~41 MB.
    The ~40 MB floor is the SQL++ core: parser + 279 builtin functions + planner + Go runtime.

what & why · the load-bearing constraint

The parser + planner is reused from cbq

        the frozen fork (couchbase/query)      n1k1 (all new code)
        ┌────────────────────────────────┐    ┌──────────────────────────┐
SQL++ ─▶│ parser ─▶ planner ─▶ plan tree ┼───▶│ conv.go ─▶ base.Op tree  │
        │                                │    │ engine.ExecOp on []byte ─┼───▶ rows
        └────────────────────────────────┘    └──────────────────────────┘
  • n1k1 takes the cbq's reference implementation's plan tree, not its executor
  • Use cbq AS-IS - no SQL++ syntax changes (yet); only minor patches needed to get cbq to build as as library.
  • Brand new datastore/virtual provides n1k1's keyspaces.
  • 100% golang secondary indexes (not GSI); pure bleve for FTS (not CBFT).
  • New capability = plan-shape recognition + new execution ops
  • Avoid new SQL++ syntax (no changes to cbq's grammar);
    @macro provides new syntax (ASOF joins, merge-scan, grep -C, query fusion, time-travel queries…).

2 · the language

SQL, generalized over JSON

nested data as a first-class citizen

sql++

No JSON operators bolted onto SQL

SELECT o.id, t AS tag
  FROM [{"id":1,"tags":["red","blue"]}] AS o
  UNNEST o.tags AS t
  -- {"id":1,"tag":"red"}
  -- {"id":1,"tag":"blue"}
  • UNNEST/NEST explode and re-nest arrays;
  • MISSING is distinct from NULL.
  • Rich object/array algebra: OBJECT_PAIRS, ARRAY_AGG, WITHIN (recursive descent), array & object comprehensions.
  • Documents are heterogeneous by default.

sql++

Fully relational

  • Nested-loop + hash joins (inner/outer, ON KEYS), LATERAL, subqueries, correlated CTEs, UNION/INTERSECT/EXCEPT.
  • Full WINDOW suite: ranking, navigation, ROWS/RANGE/GROUPS frames, named windows —
    with O(N) incremental frame folds and inverse-transition sliding (Postgres-style),
    each fast path carrying an explicit bit-exactness predicate that latches off and re-folds when violated.
  • Not RAM-bound: hash tables, sort buffers and window partitions spill dynamically
    to temp files as needed (mmap'd via github.com/couchbase/rhmap's store);
    Example: GROUP BY 64K keys runs only ~6% slower with disk spill than 1K keys in memory.

3 · the data layer

Files become keyspaces

convention over DDL · pushdown as a hint

data layer

Discovery by convention


examples/shop/           discovered keyspaces:
├─ orders/1001.json …      orders  (a dir of docs)
├─ events.jsonl            events  (multi-record file)
└─ txns.csv.gz             txns    (format sniffed per file)

FROM `./data/**/*.json`          -- backticks make a glob one identifier:
                                 -- the fork-free table-function dodge
  • Flat dirs, <namespace>/<keyspace>/ trees, globs, multiple roots (docs=~/Documents/**) —
    heterogeneous sources federate through a chain of datastore wrappers; no new scan code per source kind.
  • Doc ids carry line '#' for humans and physical byte offset '@' address: events.jsonl#57@4210 —
    so USE KEYS is an O(1) seek, not a file scan.
  • .schema command samples a keyspace and emits copy-pasteable example SQL++queries —
    for user friendliness

data layer

Parquet & Iceberg support

FROM `events@2026-01-01T00:00:00Z`  -- time travel queries
  • Pushdown for performance: predicates travel as a negation-normal-form tree in a sidecar interface;
    filter op is always kept for correctness.
  • Metadata-only answers: COUNT/MIN/MAX from Parquet footers and Iceberg manifests —
    zero data pages read; COUNT(*) over a 227 MB public-S3 Parquet answers in ~1 s.
  • iceberg-go library resolves pruning, merge-on-read deletes, and field-ID schema evolution — n1k1 just drives the scan.
  • Remote objects retrieved via ranged GETs;~0.2% of the bytes on wide tables.

data layer

VARIANT data types

  • VARIANT from Parquet = JSON's value model + typed scalars (date, timestamp, exact decimal, uuid…),
    and SQL++ on VARIANT's behave as the JSON projection - no engine changes.
  • VARIANT handled in n1k1 as yet another []byte with a 'V' prefix byte;
    encoding: V<len><VARIANT-metadata><VARIANT-value> —
    V (0x56) is outside JSON's value-start alphabet, so one byte disambiguates.
  • Zero-alloc projector: 263 ns / 0 allocs vs arrow-go's MarshalJSON at 11,858 ns / 131 allocs — ~45×;
    MarshalJSON remains the test oracle.
  • Correctness example: GROUP/DISTINCT must hash the canonical JSON projection of the VARIANT,
    never raw V prefixed bytes, since equal values can differ in encoding.

data layer

Indexes: a lazily built sidecar

.n1k1/
├─ catalog.json                       ◀ declared intent — single writer
└─ ns/ks/idx/name__si__<hash>/        ◀ content-addressed built instance
   ├─ meta.json                         (machine-managed state: never
   └─ data.bolt | bleve/                 written back to the catalog)
  • A changed index definition hashes to a new dir —
    which means an index rebuild, never in-place corruption;
    indexes build with atomic rename, orphans are lazily GC'd.
  • BBolt for seconary indexes: order-preserving key encoding means bbolt byte order == N1QL collation order,
    so Cursor.Seek prunes real range scans — and the ever-present filter catches range boundary imprecision.
  • Covering scans reconstruct the projected doc from index-key bytes,
    so no fetch needed.
  • FTS is bleve in-process — following cbq planner's FTSIndex operator, minus cbft/cbgt/n1fty/cbauth.
    Index selection stays cbq's planner: n1k1 advertise the available indexes.

data layer · fine print

Example: a 3-way nested-loop self-join

  • Consider a 3-way nested-loop self-join that expands to 262K rows:
    ~931 MB allocated with only ~3 MB live —
    garbage and GC churn, ~71% in the boxed fetch path.
  • Three n1k1 optimizations
    - native byte fetch
    - bounded per-request doc cache
    - scan key-listing cache:
    total allocations: from ~2.0 GB → ~152 MB
    GC's: from 420 → 31.

4 · the execution engine

n1k1 favors []byte's

garbage avoidance by avoiding boxed values

engine

The []byte lane

type Val []byte     // every value, in every operator
vals[5]             // hot fields promoted to positional registers as an array lookup
buf = buf[:0]       // recycle and reslice; don't reallocate
  • No interface{}
  • No map[string]interface{}
  • jsonparser returns slices into a JSON document's existing []byte.
  • Push-based — hand-off between ops and expressions is a function call (fusable/inlinable),
    not a go channel or an iterator's Next():
scan ─▶ filter ─▶ project ─▶ yield(vals)   -- plain function callbacks, optionally fused & inlined
  │        │         │
  └────────┴─────────┴────▶ yieldErr(err)  -- one error lane;
                                           -- no per-row checking of "if err != nil" anywhere
  • Results: allocs/op are flat no matter # of records processed
    — identical whether 1K rows vs 1M rows processed.
  • Raw scan throughput≈ 500M rows/s.

engine

Dual-lane expressions

31 ns · 0 B alloc's native a + b (per eval)
190 ns · 384 B alloc's same expr, boxed by cbq's engine as a fallback
  • Expressions convert to a native byte-lane form when every operand is supported;
    one unsupported operand anywhere falls the whole expression back to cbq's boxed Evaluate().
  • cbq's fallback Evaluate() is always available —
    it is the correctness oracle: every native op is differential-tested byte-identical against cbq's answers.
  • Porting is mechanical: cbq's ~357 scalar expression types collapse
    into four propagation classes (each a reused harness) over ~6 value-layer primitives.

engine

Operators share one spill substrate

  • github.com/couchbase/rhmap: robinhood maps - a recyclable map[[]byte][]byte
    that spills to mmap'd temp files — serving hash join, DISTINCT, GROUP BY, INTERSECT, EXCEPT, etc.
  • Set ops reuse the hash join's probe map (left values, left counts, probe counts) —
    INTERSECT/EXCEPT DISTINCT need no extra DISTINCT operator.
  • ORDER BY / LIMIT is a max-heap popped in reverse —
    no final sort; the heap spills too.
  • Sessions reuse spill state across queries.

engine · same parser, same planner, two executors

Boxed vs []byte, measured

6–9× faster on compute-bound work
6–26× less memory allocated
~1× on I/O-bound work (2–6× less memory)
  • Identical queries and files, and cbq's own parser+planner used by both —
    the variable: an executor that uses the boxed (value.AnnotatedValue vs an executor that uses []byte);
    the n1k1 ideal: n1k1's EXPLAIN PLAN should report zero boxed ops.
  • Example: UNNEST 20K-element arrays + GROUP BY:
    - boxed: 531 ms / 469 MB
    - []byte: 59 ms / 17.8 MB

engine · fine print

hybrid: row & columnar - they're the same lane

row batch:  Vals = [ "alice", 42, {"x":1} ]            ← one row, 3 cols
col batch:  Vals = [ ["alice","bob"], [42,43], […] ]   ← many rows
  • Val = []byte is axis-agnostic: transpose the axis and the container, push plumbing, and recycling all still apply.
    Fixed-width columnar vs row-JSON: 40–730× on arm64, no SIMD —
    the win is not-parsing + touching one stripe.
  • An Arrow buffer is a borrowed Val (zero-copy on the []byte);
    the selection vector is layout-compatible with Arrow's validity bitmap,
    so predicate ∧ validity is a byte-wise AND and one masked reducer serves both.
  • Vectorization is a post-plan rewrite by n1k1 of the group op —
    EXPLAIN runs the same pass, so the displayed plan never lies.

5 · the compiler

n1k1 is a SQL++ interpreter
and also a SQL++ compiler

one codebase, two execution modes

compiler

The lz (or "lazy") discipline

lzVal = lzA(lzVals, lzYieldErr)  // "lz" = late-bound: needs actual rows
n := len(fields)                 // early-bound: known at plan time
  • engine/*.go is a plan-tree interpreter written in a disciplined subset of Go:
    a naming convention (lz) plus comment directives mark which code is late-bound.
  • intermed_build is a line-oriented translator:
    each lazy line of code becomes a printf of itself;
    early-bound lines execute at codegen time.
            engine/*.go            -- ONE source
             │       │
      go build       intermed_build  ("lz" lines → printf's)
             │       │
             ▼       ▼
 mode 1: ExecOp      mode 2: the emitted, fused Go code for one specific SQL++ plan
 in n1k1 binary      │
 interprets any      ▼
 plan immediately    go compiler ───▶ executable binary for one specific SQL++ plan
  • Lineage: Futamura projections / LMS (Rompf & Odersky),
    LegoBase (Klonatos & Koch, VLDB'14) —
    with operator fusion and variable lifting for buffer reuse.

compiler

What gets emitted

  • .prepare <SQL++ query> emits the fused Go for the plan —
    readable, importing only n1k1's engine/ + base/:
    the whole query minus its data-access, cbq-free and cgo-free.
  • Go has no eval or dynamic loading,
    so a freshly compiled query is a separate binary —
    and n1k1's push model maps onto this split;
    the same bytes are emitted for emit-only, thin-child, fat-child, and wasm linkages:
child  = the compiled query.go binary ── drives the whole plan;
 ▲ ▼     the DatastorePipe provides: Scan / Fetch / IndexScan / Meta;
parent = n1k1, which has cbq + datasource access, and
               which streams data for the leaves of the plan to the child via DatastorePipes

compiler

BUT, is codegen / compliation worth it?

1.07–1.22× codegen speedup per row (~10 ns)
~0.1 s warm compile cost
~10M rows one-shot break-even if there's no reuse
  • Why is the speedup so low?
    Because the interpreter's already 'not too shabby'
    with n1k1's native []byte lane processing.
  • PREPARE-once / EXECUTE-many amortizes to ~10K rows at K=1000 executions —
    which points at where compilation actually pays…
  • …the huge-K regime: the next section...

multi-query

Multi-Query Optimizations

*.sql++ ×1000 ─▶ QueriesCompile ─▶ union-all( fused SQL++ detectors… )
   (in git)                         ▲ each woken only on its literal hits
                                   broadcast-indexed( scan )
                                    ▲ Aho–Corasick over each row
                                   one shared pass of the bundle
  • Broadcast —
    one shared scan feeds all SQL++ consumers:
    up to ~6.3× fewer allocs at K=256;
    CSE (common subexpression elimination) across SQL++ queries — ~2.5× at K=32 sharing one regexp.
  • Aho–Corasick predicates —
    turns O(K×rows) into ~O(hits×rows), flat in K:
    ~60× at K=1000. Invariant: the literal must be necessary (absent ⇒ predicate false),
    so over-wake is safe and under-wake never happens     — guarded by byte-identical differential testing.
    WHERE ticket.status = "open" AND ...other expressions...
  • Late binding to files — fusion keys on logical keyspace identity:
    preprocess the SQL++ queries once, assign logical-to-physical bindings at runtime as needed.

multi-query · temporal

K-way ASOF merge joins without an ASOF keyword

SELECT e.*, (SELECT r.val FROM readings r
             WHERE r.ts <= e.ts          -- nearest-preceding…
             ORDER BY r.ts DESC LIMIT 1) -- …argmax idiom
  FROM events e
  • A post-plan rewrite by n1k1 recognizes the stock correlated-argmax idiom
    and lowers it to a streaming K-way merge-join:
    O(N+M) replaces O(N×M), ~19× lower RSS memory.
    The rewrite is semantics-preserving.
  • Flink's watermark model, applied offline:
    per-file sortedness metadata (strict|near|none + a disorder_bound)
    picks concatenate / min-heap / watermarked merge —
    and output monotonicity is checked at one int64 compare per row.
  • Use case: 'grep -C'-style scans decompose into sparse match (Aho–Corasick).

multi-query · change feeds

CEP (complex event processing) with cursors

.multi cursor peek    AWS-incidents   -- the delta; cursor NOT moved
.multi cursor advance AWS-incidents   -- move + return the delta passed
  • Runs a shared-scan 'multi' set of *.sql queries but in incremental fashion,
    tracking highwater marks for each named cursor.
  • Peeking at the latest delta does not move the cursor -
    avoid auto-commit foot-guns like from Kafka.
    Re-peek after a crash can return a superset if the underlying data changed;
    per-result fingerprints give at-least-once + idempotent consumer = exactly-once effect.
  • diff mode keeps a snapshot keyed by doc id and emits Debezium-style envelopes: {op, id, before, after} —
    like a terraform-plan for arbitrary keyspaces.
  • DAG composition: 'compose' multiple queries into a DAG,
    which materializes intermediary results as temp keyspaces for dependent queries —
    providing dataflow between shared-scan queries.

multi-query · fine print

Observability for CEP

  • .multi lint is a report card for shared-scan queries —
    fused vs standalone, native vs boxed, index-pruned vs always-wake —
    these signals help developers write better fused queries.
  • gate: — a cheap precondition probed as SELECT 1 … LIMIT 1 before an expensive window/join query is run.
  • .multi explain prints the fused, shared-scan union-all(broadcast-indexed(scan)) plan plus the fusion map.

7 · extensibility

Multiple extension layers

extensibility · functions

JS UDFs: scalars & aggregates

  • A JS extension are *.js files for JS UDF's;
    or aggregate JS handlers, following git-ops practices.
  • goja (pure-Go JS) runtime is scoped per query, per actor —
    concurrent UNION ALL branches each get their own:
    no pool, no lock; JS async/Promises are disallowed.
  • Boundary hopping cost ≈ 1 µs/row —
    dominated by JS related boxing.
  • CGO_ENABLED=0 rules out .so plugins entirely;
    the end-state roadmap: goja → WASM / wazero (bounded linear memory).

7.1 · JS UDFs & aggregates — examples

A scalar UDF, and an aggregate UDF

// extensions/functions/js/slugify.js
function slugify(s) {
  return String(s)
    .toLowerCase()
    .replace(/[^a-z0-9]+/g, "-")
    .replace(/^-+|-+$/g, "");
}

// inline golden examples / tests;
// run by `.extensions test slugify`
slugify.examples = [
  {
    in: ["Hello, World!"],
    out: "hello-world"
  }
];


// geomean.agg.js — multiple callbacks for aggregates
function geomean_init() { // geometric mean aggregate
  return { logsum:0, n:0 };
}
function geomean_update(s, v) {
  if (typeof v === "number" && v > 0) {
    s.logsum += Math.log(v); s.n++;
  }
  return s;
}
function geomean_final(s) {
  return s.n ? Math.exp(s.logsum / s.n) : null;
}
// commutative merging to fold across windows/shards
function geomean_merge(a, b) {
  return {logsum:a.logsum+b.logsum, n:a.n+b.n};
}
$ n1k1 -ext ./my/path/to/js-extensions/ \
  -c 'SELECT slugify(p.category) AS slug, geomean(p.score) AS g
      FROM products p GROUP BY p.category'

extensibility · data extraction

Extract recipes: JS for custom data formats

  • JS describe(file) callback — returns a declarative spec (framing/fields/time/order),
    memoized in the .n1k1/ sidecar directory by file fingerprint;
    then the spec executes natively per record.
    One JS call per file, zero per record.
  • Imperative escape hatches when declarative spec's can't frame the data:
    extract(file, emit) (buffered) and extractStream — JS on its own goroutine,
    each emit handed over an unbuffered channel,
    so a 400 MB log will stream with bounded memory usage & backpressure.
  • describe can also specify time/order metadata:
    e.g., near-sorted-source for ASOF k-way merging —
    and, each JS extension can ship a golden test fixture
    for self-documentation and testing.

7.2 · extract JS — a describe example

apache_access.extract.js

// module scope: which files this *.extract.js can match (exts / name-regexps; highest priority wins)
var match = { exts: [".log"], names: ["access[._-].*\\.log$"], priority: 20 };

// runs ONCE per matched file, returns a DECLARATIVE spec — per-row framing then runs natively
function describe(file) { // file = { path, name, ext, head }
  return {
    format:  "apache_access_js",
    framing: { kind: "line" },
    fields:  { pattern: '^(?P<ip>\\S+) \\S+ \\S+ \\[(?P<ts>[^\\]]+)\\] ' +
                        '"(?P<method>\\S+) (?P<path>\\S+)[^"]*" (?P<status>\\d+)' },
    time:    { field: "ts", layout: "02/Jan/2006:15:04:05 -0700" },
    order:   { by: "ts", sorted: "near" } // ordering info to optimize ASOF JOIN's
  };
}

// optional examples also serve as test cases for this *.extract.js
var examples = [{
  desc: "one combined-log line -> typed fields",
  in:  '127.0.0.1 - - [10/Oct/2000:13:55:36 -0700] "GET /index.html HTTP/1.0" 200 2326\n',
  out: [ { ip: "127.0.0.1", method: "GET", path: "/index.html",
           status: "200", size: "2326", ts: 971211336000000000 } ]
}];

The above *.extract.js allows Apache log files to serve as a keyspace:

extensibility · syntax

JS macros allow users to extend SQL++ syntax

SELECT * FROM @grep_context(logs,
                            when => sev = "ERROR",
                            before => 2,
                            after => 2)
  • A motivating example: `grep -C` needs a WINDOW subquery which few can one-shot write —
    and WINDOW is syntax; and, a UDF instead can only return values.
  • Optional *.macro.js expands @name(…) at the top of n1k1's ParseStatement —
    text→text, arguments arrive as raw SQL++ substrings,
    gensym enables hygiene, innermost-first with a depth cap.
    Invisible to downstream steps: planner, CSE, MQO, and codegen all see SQL++.
  • Shipped *.macro.js examples:
    grep_context, sessionize, top_per_group, transitions;
    .macro expand shows the expansions to help developers.

7.3 · macros — the grep_context example

grep_context.macro.js

var macro = {
  name: "grep_context", params: [
    { name: "src",    required: true }, { name: "when",  required: true },
    { name: "before", default: 2},      { name: "after", default: 2 },
    { name: "order",  default: "pos" }, { name: "part" }
  ] };

function expand(args, ctx) {
  // Hygiene: every introduced name is gensym'd, so macro expansions can't collide.
  var s = ctx.gensym("src"), sub = ctx.gensym("gc"), hit = ctx.gensym("hit");
  // args.when arrived as RAW SQL++ TEXT — `sev = "ERROR"` — and is spliced verbatim.
  return "SELECT " + sub + ".*" +
         " FROM (SELECT " + s + ".*," +
                   " MAX(CASE WHEN (" + args.when + ") THEN 1 ELSE 0 END)" +
                   " OVER (ORDER BY " + args.order +
                          " ROWS BETWEEN " + args.after  + " PRECEDING" +
                          " AND " + args.before + " FOLLOWING) AS " + hit +
                " FROM " + args.src + " AS " + s + ") " + sub +
         " WHERE " + sub + "." + hit + " = 1";
}
  • NOTE: The frame bounds are swapped vs before/after —
    a perspective detail that a macro can get right instead of users figuring it out themselves.

extensibility · vectors

Vector Search, no index required (yet)

path (100K × 384, cosine top-10)time
JSONL + boxed eval11.2 s
JSONL + native byte lane6.8 s (1.6×)
columnar float32 Parquet ~0.4–0.5 s (15–29×)
  • Although unboxing to []byte lane greatly cut allocs 100M → 2M, it only provides 1.6× wall speedup —
    the reason: JSON number parsing (~38M ParseFloat calls).
    Instead, n1k1's hybrid columnar lane is the actual win,
    as the math itself is 60 ms.
  • Embeddings via VECTORIZE_BATCH;
    batching is expressed in SQL (GROUP BY pages), sugared by a @macro;
    unit tested via a deterministic fake embedding model (for CI testability).
    n1k1's limited INSERT INTO's operates in create-exclusive mode
    which serves as an embedding cache check.
  • Exact brute force to ~1M rows is cgo-free; ANN is possible roadmap (no FAISS since CGO_ENABLED=0).

7.4 · vector search — the macro that sugars it

vectorize_field.macro.js

var macro = {
 name: "vectorize_field",
 params: [
  { name:"src",   required: true },
  { name:"field", required: true },
  { name:"id",    default: "META().id" },
  { name:"batch", default: 256 },
  { name:"into",  default: "vec" },
  { name:"order", default: "" },
  { name:"opts",  default: "{}" }
 ] };
// batch = rows / round-trip to embedding model
// opts  = embedding model endpoint, dimensions, etc.

function expand(args, ctx) {
 var k   = ctx.gensym("k"),  rows = ctx.gensym("rows"),
     pg  = ctx.gensym("pg"), emb  = ctx.gensym("emb"),
     row = ctx.gensym("row"), …;

 … (continued)

 var order = (args.order && args.order.replace(/\s/g, "") !== "") ? args.order : args.id;
 // Force text/into onto the caller's opts (they can't be overridden): the batch objects
 // are {id,text}, so VECTORIZE_BATCH must read "text" and write the requested field.
 var vopts = 'OBJECT_PUT(OBJECT_PUT(' + args.opts + ', "text", "text"), "into", "' + args.into + '")';

 return "(SELECT " + row + ".* FROM (" +
   "SELECT VECTORIZE_BATCH(" + pg + ".b, " + vopts + ") AS b FROM (" +
     "SELECT ARRAY_AGG({\"id\": " + rows + "." + idc + ", \"text\": " + rows + "." + txt + "}) AS b FROM (" +
       "SELECT (" + args.id + ") AS " + idc + ", (" + args.field + ") AS " + txt + ", " +
              "ROW_NUMBER() OVER (ORDER BY " + order + ") AS " + rn +
       " FROM " + args.src + " AS " + k +
     ") AS " + rows +
     " GROUP BY FLOOR((" + rows + "." + rn + " - 1) / " + args.batch + ")" +
   ") AS " + pg +
 ") AS " + emb + " UNNEST " + emb + ".b AS " + row + ")";
}
// @vectorize_field(...) expands to this (gensym'd names simplified) — page by ROW_NUMBER, ARRAY_AGG each page,
// ONE embedding model call per page (not per row), UNNEST back to per-row {id, text, vec}.
(SELECT row.* FROM (SELECT VECTORIZE_BATCH(pg.b, <vopts>) AS b
   FROM (SELECT ARRAY_AGG({"id": rows.id, "text": rows.txt}) AS b
           FROM (SELECT (META().id) AS id, (line) AS txt,
                        ROW_NUMBER() OVER (ORDER BY META().id) AS rn
                   FROM logs AS k) AS rows
          GROUP BY FLOOR((rows.rn - 1) / 256)) AS pg) AS emb
 UNNEST emb.b AS row)

8 · engineering rigor

cbq's reference implementation
is a SQL++ test oracle

rigor

Differential everything

  • cbq's own live-cluster integration SQL++ corpus (68 categories, ~2,352 statements) mined into file-datastore fixtures: n1k1 must match cbq byte-for-byte, in interpreter and compiled modes,
    gated by regression floors (1045 defaults / 833 gsi).
  • Compiler validation is two mandatory phases — generate, and build and run the generated Go.
  • Non-passes are explicit and rationale-tagged —
    including cases where n1k1 declines to match cbq's quirks (single-element VAR_SAMP=0, numeric RANGE frames over non-numeric keys).

rigor and gotchas

How to be wrong
about your SQL++ engine

  • Time the full request — an ExecOp-only measurement once showed a bogus ~40× "win" :-(
  • Validate row counts, not just speedups —
    a parallel-scan prototype silently dropped 18% of rows (20,000 → 16,384 = 256×64) -
    unflushed final batches while looking fast. :-(
  • Float SUM is non-deterministic under reordering -
    rounding error drift trips exact-diff test cases. :-(
  • Compiled-child memory usage was uncounted by the parent n1k1 process. :-( and more

rigor and Amdahl's Law

I/O - the biggest wins aren't in the engine

3194 ms 20,000 one-doc files, serial scan
703 ms same, 128 parallel actors
13 ms same docs, one .jsonl file
  • Packing into 1 file beats parallelizing by an order of magnitude (~245× vs serial):
    at 128 actors, 97.6% of time is syscall.syscall.
    The concurrency ceiling was data layout, not the engine.
  • Same spirit at the microsecond end: raw SELECT 0 is 27.9 µs — ~94% of that in parse+plan.
    Prepared: 1.6 µs, ~1.55M q/s across goroutines.

rigor · fine print

-race detector stories

  • UNION-ALL bug bit three times, each caught by -race;
    lesson: per-actor mutable state needs to live in a per-actor data clone,
    not in shared context.
  • Inverted use: the stats core in n1k1 is a flat []int64
    bumped without atomics, justified by assuming there's a single-writer-per-slot —
    -race turned a violated assumption into a visible write/write race.

the through-line

Five decisions (at least)

  • []byte is better than parsed objects (boxes) in performance (speed and memory usage).
  • Hybrid row and columnar -
    relatively easy when everything travels as []byte.
  • A frozen SQL++ grammar from cbq forced n1k1
    to optimize via plan-shape pattern recognition and new runtime ops —
    which allowed n1k1 features to be composable.
  • Must-Have for evaluation / verification:
    trusted oracles to stand upon - for n1k1, that's cbq.
  • The best optimizations were layout and metadata —
    and, the cheapest read is the one you skip.
