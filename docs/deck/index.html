couchbase/n1k1 · SQL++

n1k1

SQL++ for local files and more —
with a high performance query engine that's
both an interpreter and a compiler.

design & tech choices

1

1 · what & why

Query local files and more

no server · no import step · no schema to declare

what & why

One binary, pointed at a directory

$ n1k1 -c "SELECT id, customer, total FROM orders
           WHERE total > 200 ORDER BY total DESC" examples/shop
  • Think sqlite3 / duckdb, but the query language is built for nested JSON and the scan layer treats a directory tree of mixed formats as tables.
  • Formats are discovered per file — no CREATE TABLE:

JSON / JSONLCSV / TSVYAML TOMLParquetIceberg .gzPDF / Offices3:// gs:// abfs://

Box table at a terminal, JSON Lines when piped — composes with jq & friends. Also compiles to wasm: the playground runs n1k1's engine client-side in a browser.

what & why

Deliberately not a database server yet

  • Read-oriented: no UPDATE/DELETE, no transactions. Writing is materialization only (CREATE TEMP KEYSPACE, INSERT INTO a .jsonl/Parquet file).
  • Pure Go, CGO_ENABLED=0, cross-compiles to Linux/macOS/Windows on amd64 + arm64 — and to GOOS=js/wasm.
  • Goroutine-per-connection sessions — a CLI and a library, not a daemon yet.
  • Binary anatomy: full build ~102 MB; -tags trim (drop lakehouse + cloud SDKs) ~41 MB. The irreducible ~40 MB floor is the SQL++ surface itself: parser + 279 builtin functions + planner + Go runtime.

what & why · the load-bearing constraint

The parser + planner is from cbq

        the frozen fork (couchbase/query)      n1k1 (all new code)
        ┌────────────────────────────────┐  ┌──────────────────────────┐
SQL++ ─▶│ parser ─▶ planner ─▶ plan tree ┼─▶│ conv.go ─▶ base.Op tree  │
        │                                │  │ engine.ExecOp on []byte ─┼─▶ rows
        └────────────────────────────────┘  └──────────────────────────┘
  • n1k1 takes the cbq's reference implementation's plan, not its executor — cbq boxes a value per tuple/field; n1k1's engine is the opposite bet.
  • Try to use cbq AS-IS - no SQL++ syntax changes (yet); minor patches to get cbq to build. Brand new datastore/virtual fakes keyspaces. 100% golang secondary indexes (not GSI); pure bleve for FTS (not CBFT).
  • New capability = plan-shape recognition + new runtime ops, never new SQL++ syntax, but @macro's are ok (ASOF joins, merge-scan, grep -C, query fusion, time-travel queries…).

2 · the language

SQL, generalized over JSON

nested data as a first-class citizen

sql++

No JSON operators bolted onto SQL

SELECT o.id, t AS tag
  FROM [{"id":1,"tags":["red","blue"]}] AS o
  UNNEST o.tags AS t
-- {"id":1,"tag":"red"}  {"id":1,"tag":"blue"}
  • UNNEST/NEST explode and re-nest arrays; MISSING is distinct from NULL.
  • Rich object/array algebra: OBJECT_PAIRS, ARRAY_AGG, WITHIN (recursive descent), array & object comprehensions.
  • Documents are heterogeneous by default — the opaque-document path: a record is one self-value, so mixed shapes just work.

sql++

The full relational surface — spillable

  • Nested-loop + hash joins (inner/outer, ON KEYS), LATERAL, subqueries, correlated CTEs, UNION/INTERSECT/EXCEPT.
  • Full WINDOW suite: ranking, navigation, ROWS/RANGE/GROUPS frames, named windows — with O(N) incremental frame folds and inverse-transition sliding (Postgres-style), each fast path carrying an explicit bit-exactness predicate that latches off and re-folds when violated.
  • Nothing is RAM-bound: hash tables, sort buffers and window partitions spill dynamically to temp files as needed (mmap'd rhmap/store); GROUP BY over 64K keys with spill runs only ~6% slower than 1K keys in memory.

sql++ · fine print

Rosetta Stone comparison recipes

Common JSON slice-and-dice tasks, each shown side-by-side in SQL++ vs SQL (Postgres, DuckDB), JavaScript, Python, MongoDB, and jq syntax — generated from one YAML source, published with per-recipe permalinks.

3 · the data layer

Files become keyspaces

convention over DDL · pushdown as a hint

data layer

Discovery by convention


examples/shop/           discovered keyspaces:
├─ orders/1001.json …      orders  (a dir of docs)
├─ events.jsonl            events  (multi-record file)
└─ txns.csv.gz             txns    (format sniffed per file)

FROM `./data/**/*.json`          -- backticks make a glob one identifier:
                                 -- the fork-free table-function dodge
  • Flat dirs, <namespace>/<keyspace>/ trees, globs, multiple roots (docs=~/Documents/**) — heterogeneous sources federate through a chain of datastore wrappers; no new scan code per source kind.
  • Doc ids carry the physical byte offset address: events.jsonl#57@4210 — so USE KEYS is an O(1) seek, not a file scan.
  • .schema samples a keyspace and emits copy-pasteable example queries — schema inference as UX.

data layer

Parquet & Iceberg, cgo-free

FROM `events@2026-01-01T00:00:00Z`  -- time travel, no grammar change
  • Pushdown's: predicates travel as a negation-normal-form tree in a sidecar interface; the residual filter op is always kept, so a partial or absent push is correct, never wrong.
  • Metadata-only answers: COUNT/MIN/MAX from Parquet footers and Iceberg manifests — zero data pages read; COUNT(*) over a 227 MB public-S3 Parquet answers in ~1 s.
  • Iceberg reader glue is ~90 lines: iceberg-go already resolves pruning, merge-on-read deletes, and field-ID schema evolution — n1k1 just drives the scan.
  • Remote objects read via ranged GETs; projection pushdown reads ~0.2% of the bytes on wide tables.

data layer

VARIANT: query the JSON projection

  • VARIANT = JSON's value model + typed scalars (date, timestamp, exact decimal, uuid…), and SQL++ on VARIANT's behave as the JSON projection - no engine changes. Lossy-in-arithmetic, lossless-in-transit.
  • VARIANT just rides as []byte with a 'V' prefix byte and encoding: V<len><VARIANT-metadata><VARIANT-value> — V (0x56) is outside JSON's value-start alphabet, so one byte disambiguates.
  • Zero-alloc projector: 263 ns / 0 allocs vs arrow-go's MarshalJSON at 11,858 ns / 131 allocs — ~45×; MarshalJSON kept as the test oracle.
  • Correctness example: GROUP/DISTINCT must hash the canonical JSON projection, never raw V bytes — equal values can differ in encoding.

data layer

Indexes: a lazily built sidecar

.n1k1/
├─ catalog.json                       ◀ declared intent — single writer
└─ ns/ks/idx/name__si__<hash>/        ◀ content-addressed built instance
   ├─ meta.json                         (machine-managed state: never
   └─ data.bolt | bleve/                 written back to the catalog)
  • A changed index definition hashes to a new dir — a rebuild, never in-place corruption; builds with atomic rename, orphans are lazily GC'd.
  • BBolt for seconary indexes: order-preserving key encoding means bbolt byte order == N1QL collation order, so Cursor.Seek prunes real range scans — and the ever-present residual filter catches range boundary imprecision.
  • Covering scans reconstruct the projected doc from index-key bytes, so no fetch needed.
  • FTS is bleve in-process — following cbq planner's FTSIndex operator, minus cbft/cbgt/n1fty/cbauth. Index selection stays cbq's planner: n1k1 has control over what its datastore advertises as the available indexes.

data layer · fine print

Fetch-path allocations

  • Consider a 3-way nested-loop self-join that expands to 262K rows: ~931 MB allocated with only ~3 MB live — garbage and GC churn, ~71% in the boxed fetch path.
  • Three n1k1 optimizations - native byte fetch, bounded per-request doc cache, scan key-listing cache): from ~2.0 GB → ~152 MB total allocation, GCs from 420 → 31.

4 · the execution engine

Everything is []byte

garbage avoidance is an architectural foundation, not a tuning pass

engine

The byte lane

type Val []byte     // every value, in every operator
vals[5]             // hot fields promoted to positional registers
buf = buf[:0]       // recycle; reslice, don't reallocate
  • No interface{}, no map[string]interface{}; jsonparser returns slices into the document's existing bytes.
  • Push-based — hand-off is a function call (fusable/inlinable), not a channel or an iterator:
scan ─▶ filter ─▶ project ─▶ yield(vals)   -- plain calls, fused/inlined
  │        │         │
  └────────┴─────────┴────▶ yieldErr(err)  -- one error lane: no per-row
                                           -- "if err != nil" anywhere
  • Results: allocs/op are flat no matter # of records processed — scan 6, +filter 18, +project 37, identical whether 1K rows vs 1M rows. Raw scan ≈ 500M rows/s.

engine

Dual-lane expressions

31 ns · 0 B alloc's native a + b (per eval)
190 ns · 384 B alloc's same expr, boxed by cbq's engine as a fallback
  • Expressions convert to a native byte-lane form when every operand is supported; one unsupported operand anywhere falls the whole expression back to cbq's boxed Evaluate().
  • cbq's fallback is never removed — it is the correctness oracle: every native op is differential-tested byte-identical against cbq's answers.
  • Porting is mechanical: cbq's ~357 scalar expression types collapse into four propagation classes (each a reusable harness) over ~6 value-layer primitives.

engine

One spill substrate, many operators

  • rhmap: robinhood maps - a recyclable map[[]byte][]byte that spills to mmap'd temp files — serving hash join, DISTINCT, GROUP BY, INTERSECT, EXCEPT.
  • Set ops reuse the hash join's probe map (left values, left counts, probe counts) — INTERSECT/EXCEPT DISTINCT need no extra DISTINCT operator.
  • ORDER BY / LIMIT is a max-heap popped in reverse — no final sort; the heap spills too.
  • Sessions reuse spill state across queries (pools cleared, not just parked): ~2.3× throughput on a single-file query mix.

engine · same parser, same planner, two executors

Boxed vs []byte, measured

6–9× faster on compute-bound work
6–26× less memory allocated
~1× on I/O-bound work (2–6× less memory)
  • Identical queries and files, and cbq's own parser+planner used by both — the variable: an executor that uses (value.AnnotatedValue vs an executor that uses []byte); the n1k1 ideal: n1k1's EXPLAIN PLAN shows zero boxed markers.
  • Example: UNNEST 20K-element arrays + GROUP BY: 59 ms / 17.8 MB vs 531 ms / 469 MB.

engine · fine print

hybrid: columnar lane is the same lane

row batch:  Vals = [ "alice", 42, {"x":1} ]            ← one row, 3 cols
col batch:  Vals = [ ["alice","bob"], [42,43], […] ]   ← many rows
  • Val = []byte is axis-agnostic: transpose the axis and the container, push plumbing, and recycling all still apply. Fixed-width columnar vs row-JSON: 40–730× on arm64, no SIMD — the win is not-parsing + touching one stripe.
  • An Arrow buffer is a borrowed Val (zero-copy on the []byte); the selection vector is layout-compatible with Arrow's validity bitmap, so predicate ∧ validity is a byte-wise AND and one masked reducer serves both.
  • Vectorization is a post-plan rewrite by n1k1 of the group op — EXPLAIN runs the same pass, so the displayed plan never lies.

5 · the compiler

n1k1 is an interpreter that is also a compiler

one codebase, two execution modes

compiler

The lz (or "lazy") discipline

lzVal = lzA(lzVals, lzYieldErr)  // "lz" = late-bound: needs actual rows
n := len(fields)                 // early-bound: known at plan time
  • engine/*.go is a plan-tree interpreter written in a disciplined subset of Go: a naming convention (lz) plus comment directives mark which lines are late-bound.
  • intermed_build is a line-oriented translator: each lazy line of code becomes a printf of itself; early-bound lines execute at codegen time.
           engine/*.go            -- ONE source
            │        │
     go build        intermed_build  ("lz" lines → printf's)
            ▼        ▼
 mode 1: ExecOp     intermed/ ─▶ mode 2: emit the fused Go
 interprets any                  for one specific plan
 plan, immediately
  • Lineage: Futamura projections / LMS (Rompf & Odersky), LegoBase (Klonatos & Koch, VLDB'14) — with operator fusion and variable lifting for buffer reuse.

compiler

What gets emitted

  • .prepare <SQL++ query> emits the fused Go for the plan — readable, importing only engine/ + base/: the whole query minus its data-access, cbq-free and cgo-free.
  • Go has no eval or dynamic loading, so a freshly compiled query is a separate binary — and n1k1's push model maps onto this split; the same bytes are emitted for emit-only, thin-child, fat-child, and wasm linkages:
child  = the compiled query.go binary ── drives the whole plan
   ▲ ▼  DatastorePipe: Scan / Fetch / IndexScan / Meta
parent = has cbq + the data ──────────── serves the leaves

compiler

BUT, is it worth it?

1.07–1.22× codegen speedup per row (~10 ns)
~0.1 s warm compile cost
~10M rows one-shot break-even if there's no reuse
  • Why so low? Because the interpreter's already good with n1k1's native []byte lane processing.
  • PREPARE-once / EXECUTE-many amortizes to ~10K rows at K=1000 executions — which points at where compilation actually pays…
  • …the huge-K regime: the next section.

6 · many queries, one scan

MQO (multi-query optimization), temporal joins & CEP (complex event processing)

driven by a git repo of SQL++ queries as the workload

multi-query

Corpus fusion (PREPARE++)

*.sql++ ×1000 ─▶ CorpusCompile ─▶ union-all( fused detectors… )
   (in git)                            ▲ each woken only on its literal hits
                                 broadcast-indexed( scan )
                                       ▲ Aho–Corasick over each row
                                 one shared pass of the bundle
  • Broadcast — one scan feeds all consumers: up to ~6.3× fewer allocs at K=256; CSE (common subexpression elimination) across SQL++ queries — ~2.5× at K=32 sharing one regexp.
  • Aho–Corasick predicate index — turns O(K×rows) into ~O(hits×rows), flat in K: ~60× at K=1000. Invariant: the literal must be necessary (absent ⇒ predicate false), so over-wake is safe and under-wake never happens — guarded by byte-identical differential testing.
  • Late binding to files — fusion keys on logical keyspace identity: compile the corpus once, rebind per bundle; the binding is data, not code.

multi-query · temporal

K-way ASOF merge joins without an ASOF keyword

SELECT e.*, (SELECT r.val FROM readings r
             WHERE r.ts <= e.ts          -- nearest-preceding…
             ORDER BY r.ts DESC LIMIT 1) -- …argmax idiom
  FROM events e
  • A post-plan rewrite recognizes the stock correlated-argmax idiom and lowers it to a streaming K-way merge-join: O(N+M) replacing O(N×M), ~19× lower RSS. False negative costs speed; the rewrite is semantics-preserving by construction.
  • Flink's watermark model, applied offline: per-file sortedness metadata (strict|near|none + a disorder_bound) picks concatenate / min-heap / watermarked merge — and output monotonicity is checked at one int64 compare per row, because a wrong bound silently corrupts a merge.
  • grep -C decomposes into sparse match (Aho–Corasick) + bounded ring-buffer expansion — beats general WINDOW machinery for the idiom.

multi-query · change feeds

Named cursors: CEP (complex event processing)

.multi cursor peek    incidents   -- the delta; cursor NOT moved
.multi cursor advance incidents   -- move + return the delta passed
  • Crash-safety in one line: getting the delta must not move the cursor (avoiding auto-commit foot-gun's like from Kafka). Re-peek after a crash returns a superset; per-result fingerprints give at-least-once + idempotent consumer = exactly-once effect.
  • diff mode keeps a snapshot keyed by doc id and emits Debezium-style envelopes: {op, id, before, after} — like a terraform-plan for arbitrary keyspaces.
  • GitOps for standing monitors: a directory or pack of *.sql++ reconciles via plan/apply [--prune]; the identity hash deliberately excludes metadata, so a reworded description doesn't reset a cursor.
  • DAG composition: each pack node's results materialize as a temp keyspace the next node FROMs — the replay journal is the inter-pack dataflow.

multi-query · fine print

Observability for a corpus

  • .multi lint is a report card per detector — fused vs standalone, native vs boxed, index-pruned vs always-wake — the signals to help developers succeed.
  • gate: — a cheap precondition probed as SELECT 1 … LIMIT 1 before an expensive window/join query is run; skips are reported, never silent.
  • .multi explain prints the fused MQO union-all(broadcast-indexed(scan)) plan plus the fusion map.

7 · programmability

Three extension layers

values · files · syntax — kept religiously distinct

extensibility · values

JS UDFs: functions & aggregates

  • A JS extension author provides *.js files to specify either JS UDF's or aggregate JS handlers, to follow git-ops practices.
  • goja (pure-Go JS) runtimes are scoped per query, per actor — concurrent UNION ALL branches each get their own: no pool, no lock; JS async/Promises are rejected rather than hanging.
  • Boundary hopping cost ≈ 1 µs/row — dominated by JS related boxing.
  • CGO_ENABLED=0 rules out .so plugins entirely; the end-state ladder is goja → wazero (bounded linear memory = isolation goja can't give).

extensibility · files

Extract recipes: JS for custom data formats

  • JS describe(file) callback — returns a declarative spec (framing/fields/time/order), memoized in the .n1k1 sidecar by file fingerprint; then the spec executes natively per record. One JS call per file, zero per record.
  • Imperative escape hatches when declarative spec's can't frame the data: extract(file, emit) (buffered) and extractStream — JS on its own goroutine, each emit handed over an unbuffered channel, so a 400 MB log streams with bounded memory usage with backpressure.
  • describe can also specify time/order metadata: e.g., near-sorted-source for ASOF k-way merging — and, each JS plugin ships a golden fixture (a wrong bound is a silent merge risk).

extensibility · syntax

JS Macros, because UDFs can't make SQL++ syntax

SELECT * FROM @grep_context(logs, when => sev = "ERROR",
                            before => 2, after => 2)
  • A motivating example: `grep -C` needs a WINDOW subquery which few can one-shot write — and WINDOW is syntax; a scalar UDF returns values.
  • Optional *.macro.js expands @name(…) at the top of ParseStatement — text→text, arguments arrive as raw SQL++ substrings, gensym enables hygiene, innermost-first with a depth cap. Invisible to downstream steps: planner, CSE, MQO, and codegen all see SQL++.
  • Shipped starters: grep_context, sessionize, top_per_group, transitions; .macro expand shows the expansions to help developers.

extensibility · vectors

Vector Search, no index required (yet)

path (100K × 384, cosine top-10)time
JSONL + boxed eval11.2 s
JSONL + native byte lane6.8 s (1.6×)
columnar float32 Parquet ~0.4–0.5 s (15–29×)
  • It's counterintuitive, although unboxing greatly cut allocs 100M → 2M, it only provides 1.6× wall speedup — the reason: JSON number parsing (~38M ParseFloat calls). Instead, n1k1's hybrid columnar lane is the actual win, as the math itself is 60 ms.
  • Embeddings via VECTORIZE_BATCH; batching is expressed in SQL (GROUP BY pages), sugared by a @macro; unit tested via a deterministic fake embedding model (for CI testability). n1k1's limited INSERT INTO's operates in create-exclusive mode as a 'free' embedding cache check.
  • Exact brute force to ~1M rows is cgo-free; ANN is future (no FAISS since CGO_ENABLED=0).

8 · engineering rigor

cbq's reference implementation
is a SQL++ test oracle

and other ways to avoid fooling yourself

rigor

Differential everything

  • cbq's own live-cluster integration SQL++ corpus (68 categories, ~2,352 statements) mined into file-datastore fixtures: n1k1 must match cbq byte-for-byte, in interpreter and compiled modes, gated by regression floors (1045 defaults / 833 gsi).
  • Compiler validation is two mandatory phases — generate, then actually build and run the generated Go.
  • Non-passes are explicit and rationale-tagged — including cases where n1k1 declines to match cbq's quirks (single-element VAR_SAMP=0, numeric RANGE frames over non-numeric keys) rather than green-washing the number.

rigor · measurement gotchas, hard-won

How to be confidently wrong
about your own engine

  • Time the full request — an ExecOp-only measurement once showed a bogus ~40× "win" :-(
  • Validate row counts, not just speedups — a parallel-scan prototype silently dropped 18% of rows (20,000 → 16,384 = 256×64: unflushed final batches) while looking fast. :-(
  • Float SUM is non-deterministic under reordering (rounding error drift trips exact-diff oracles); compiled-child memory usage was uncounted by the parent; and more

rigor · the humbling result

I/O - the biggest wins were never in the engine

3194 ms 20,000 one-doc files, serial scan
703 ms same, 128 parallel actors
13 ms same docs, one .jsonl file
  • Packing into 1 file beats parallelizing by an order of magnitude (~245× vs serial): at 128 actors, 97.6% of time is syscall.syscall. The concurrency ceiling is the layout, not the engine.
  • Same spirit at the microsecond end: raw SELECT 0 is 27.9 µs — ~94% parse+plan. Prepared: 1.6 µs, ~1.55M q/s across goroutines.

rigor · fine print

-race detector stories

  • The UNION-ALL-shares-one-context bug class bit three times, each caught by -race; lesson: per-actor mutable state lives behind the per-actor clone, not the shared context.
  • Inverted use: the stats core is a flat []int64 bumped without atomics, justified by single-writer-per-slot — -race turns a violated assumption into a visible write/write race instead of a silently wrong count.
  • Measurement counters cost no time.Now() on the row path; rendering happens at ~10 Hz on the reader side (the ClickHouse/DuckDB cadence discipline).

the through-line

Five decisions (at least)

  • []byte is better than parsed objects (boxes) in performance (speed and memory usage).
  • Hybrid row and columnar -- turned out to be not a problem when everything's a []byte.
  • A frozen SQL++ grammar from cbq forced n1k1 to optimize via plan-shape recognition and new runtime ops — which allowed features to be composable.
  • The evaluation / verification must-have: the trusted oracle to stand upon - for n1k1, that's cbq.
  • The best optimizations were layout and metadata — the cheapest read is the one you skip.
